  9. Compare the step's assembly version and the trace output between a fast baseline execution and a slow current one.
  10. Open one of the chains in the Trace explorer (Chain ◀ ▶) and read the failures in order of depth and start time.
  11. Check whether the deepest failure's message appears inside the shallower failures' messages.
  12. Check whether the step updates attributes that are in its own filtering attributes, and whether it guards with context.Depth.
  13. List every step registered on Create of account and check their order (stage and rank) and filtering attributes.
  14. Compare the input data of failing and succeeding executions, if trace output records it.
  15. Treat correlations for these traces as heuristic leads only.
  16. Write the identifiers you need into the trace output (ITracingService) so they appear in the message block.

9. Notes and limitations

  • Plug-in trace logs are only written when tracing is enabled, and Dataverse deletes them after a retention period. Missing traces are not evidence that no failures happened.
  • Correlation ID links traces in one causal chain, which can span several operations and asynchronous continuations. It does not prove that two traces are the same operation.
  • Parent/child relationships are inferred from depth and timing and are labelled as suspected. Dataverse does not record them.
  • Heuristic correlations (no shared identifier) are leads to check, not proof of a shared transaction.
  • Possible explanations are hypotheses that guide the investigation. They are not confirmed root causes.
  • An execution is only called slow when its recorded duration meets the configured threshold for its execution mode.
